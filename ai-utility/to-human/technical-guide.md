# プロフィール概要の取得

`scc user [username] --section about` は、Scratchのプロフィールページを1回取得し、`#profile-data` 内から自己紹介、近況、ユーザー種別、参加日、国を抽出する。ログイン中の本人ページは編集用の `#bio textarea` と `#status textarea`、他人のページは閲覧用の `#bio-readonly .overview` と `#status-readonly .overview` を使用する。

注目のプロジェクトは Scapi と同じサイトAPIを1回取得する。Scapi 3.2.4 の `ProjectFeatured` はラベルIDを固定のEnumへ変換し、未知のIDで例外になるため、APIが返す `featured_project_label_name` を優先して見出しに使う。名前がない場合だけ既知IDから補う。作品が設定されていなければ `None` とする。

最近の活動はHTMLの `#activity-feed` に初期状態では含まれず、ブラウザが後から取得する。CLIは Scapi の `User.get_activities(10)` を1回呼び出して先頭10件まで表示し、追加ページを自動取得しない。

フォロー状態は認証済みで表示した対象のプロフィールHTMLの `#follow-button [data-control]` を読み、`follow` / `unfollow` をそれぞれ未フォロー / フォロー中と解釈する。本人ページも `Following: Self` ではなく `Yes` / `No` / `Unknown` を表示する。`details` ではScapiの `load_website()` に加えて状態確認のため対象ページを1回読む。`about` は既存のページ応答を再利用する。

本人ページにフォローボタンがない場合は、`following.py` の共通処理が Scapi の `User.get_followings(limit=40, offset=0)` で最初の1ページだけ確認する。自分のユーザー名が大文字小文字を無視して一致すれば `Yes`、有効な一覧が40件未満で終わり一致しなければ `No` とする。40件に達して見つからない場合やデータが不正な場合は、続きに自分が含まれる可能性があるので `Unknown` とする。途中で見つかった場合も `aclosing` でジェネレーターを閉じ、次ページの取得や自動再試行は行わない。他人のページや未ログイン時はこの追加取得を行わない。

HTMLにない任意項目は `None` または空の一覧として扱う。`#profile-data` と表示名がないページは正常なプロフィールとして扱わず、エラーを返す。ユーザーIDはアバター画像URLから取得できる場合のみ表示する。作品・お気に入りなどの一覧取得は従来どおりScratch APIを使用する。

## ユーザー関連コマンドの統合

`scc user [username] --section <section>` をユーザー関連情報の正式な入口とする。`details` は従来の `user` が使っていたログイン必須の詳細取得へ、それ以外のsectionは従来の `profile` 処理へ振り分ける。この振り分けにより、公開プロフィール取得時のリクエスト数や認証情報の扱いを変更せず、CLIだけを単純化している。

公開コマンドの `profile`、`user --user` / `-u`、引数なしの `account` は廃止している。ユーザー名は `user` の位置引数に統一し、`account` には操作名を必須とする。yargsの厳密な引数検証で旧形式を通信前に拒否する。`src/commands/profile.ts` とPython側のプロフィール取得処理は `user --section` から利用する内部処理として残し、公開コマンドの削除によって取得機能まで失われないようにしている。

## Scratchトップページのsection取得

`scc home` はsectionを1つずつ取得する。注目作品、注目スタジオ、Scratch Design Studioは同じfeatured APIレスポンスに含まれるが、一度の実行では指定されたsectionだけを表示し、他sectionの追加取得は行わない。Scratch Design Studioの題名は固定せず、APIが返す現在のスタジオ名を見出しに使用する。

`whats-happening` と `following-loves` はアクティブアカウントに依存するため、セッションIDをコマンドライン引数へ含めず標準入力でPythonへ渡す。公開sectionでは設定ファイルを読み込まず、認証なしのクライアントを使う。全sectionの一括取得を既定動作にせず、section未指定時は利用可能な名前だけを表示することで不要なAPIリクエストを防いでいる。

Scapiの `get_community_featured()` に既に含まれる人気の好き・リミックス・新着作品も、指定された1種類だけ表示する。フォロー中ユーザーの共有作品、フォロー中スタジオの作品、閲覧履歴はセッションの個別メソッドを使い、指定件数と開始位置だけ取得する。

ホームの取得エラーは、Scapiの `ProcessingError`（接続失敗・タイムアウト）、HTTP 429、認証失効、権限不足、404、サーバーエラー、不正な応答を区別する。429では `Retry-After` の秒数・HTTP日付が読める場合に待機時間を案内するが、自動再試行しない。個人フィードでは認証時の `ValueError` と、認証後のデータ変換時の `ValueError` を分ける。後者で再ログインを要求しても解決しないためである。例外本文・Pythonの標準エラー・取得本文を診断メッセージへ流さず、保存済みのログインも消去しない。

## Scapiを使った作品・ユーザー操作

作品の好き・お気に入りには `Project.add_love()` / `remove_love()` と `add_favorite()` / `remove_favorite()`、フォローには `User.follow()` / `unfollow()` を使用する。コメントは作品・ユーザーともに `post_comment()` を使う。ScapiはユーザープロフィールへのコメントだけScratchの旧APIへ自動的に切り替えるため、CLI側でエンドポイントを直接組み立てない。

TypeScriptからPythonへは、操作種別と公開対象だけをプロセス引数で渡し、セッションIDとコメント本文はJSONとして標準入力へ渡す。Python側はScapiの公開メソッドを1回だけ呼び、成功したアカウント名、対象、操作、コメントIDなど、表示に必要な最小限の情報だけをJSONで返す。コメントがScratchのフィルターに拒否された場合も本文をエラーへ含めない。

コメントはScratch公式Webクライアントと同じく500文字を上限とし、空文字や上限超過は通信前に拒否する。これらの操作では失敗時に自動再試行しないため、重複コメントや意図しない反応の再送を防げる。

## My Stuffと作成系操作

自分の作品一覧は `Session.get_mystuff_projects()` を使い、`all`、`shared`、`notshared`、`trashed` をそのままScapiへ渡す。このAPIはページ単位なので、CLIの `--page` で指定した1ページだけを取得し、後続ページを自動取得しない。

空プロジェクトとスタジオの作成には `Session.create_project()` と `Session.create_studio()`、スタジオ招待の承認には `Studio.accept_invite()` を使用する。いずれも成功時に操作アカウントと作成・参加対象のIDを表示する。認証情報は他のPython処理と同様に標準入力だけで受け渡す。

## リミックスと変更操作の安全確認

Scapi 3.2.4 の `Project.create_remix()` はリミックス関係だけを付けた空作品を作成し、元作品の中身を複製しない。CLIでは、まず `Session.get_project()` でトークン付きの `Project.download_url` を得て、元作品のJSONを取得する。そのバイト列をJSONとして明示し、`Session.create_project(project_data=..., remix_id=..., is_json=True)` に渡す。元データが取得できない、または空の場合は空作品へフォールバックせず中止する。アセットはプロジェクトJSON内の既存参照を引き継ぐ。

作成・リミックス・招待承認から、共有、ゴミ箱移動、スタジオの昇格・削除、プロフィール・設定変更まで、TypeScript側が先にアクティブなScratchユーザー名を取得して、アカウント、対象、変更内容を表示する。対話端末で `yes` が入力されたときだけ変更用プロセスを開始する。変更用プロセスは同じユーザー名を `expected_account` として受け取り、ログイン後のユーザー名が一致しなければScapiの変更メソッドを呼ばない。この二重確認により、確認表示から実行までにセッションが切り替わった場合の誤操作を防ぐ。

確認必須操作は標準入力がTTYでなければ即座に失敗する。確認を省略するオプションはなく、自動化環境で意図せず公開・削除・プロフィール変更が実行されることはない。セッションIDと変更データはPythonプロセスの標準入力へ渡し、コマンドライン引数へ含めない。

## 追加のScapi操作と機密データの受け渡し

作品・スタジオの編集、ゴミ箱からの復元、サムネイル変更、スタジオへの作品追加、報告、Scratcher昇格、メール変更、アカウント削除も同じ確認層を通す。TypeScript側で操作前後のアカウント一致を保証し、Python側も `expected_account` の欠落や不一致を拒否する。報告と削除の単体テストはScapiオブジェクトをモックし、実際のScratchデータへは送信しない。

サムネイルはCLI側で存在、1 byte～5 MiB、PNG/JPEG/GIFのマジックバイトを検査し、base64として標準入力へ渡す。Python側でもbase64を検証してからScapiへbytesを渡す。これにより画像データやパスをプロセス引数へ展開しない。

メール変更とアカウント削除のパスワードはCLIオプションにせず、Node互換のTTY raw modeでエコーを止めて読み取る。外部の `stty` コマンドに依存しないため、Windows、macOS、Linuxで同じ経路を利用できる。アカウント削除は通常の `yes` より強い `delete <account>` を要求し、Scapi側が成功した場合だけ保存済みセッションを削除する。

## クラス管理・所有権移譲・パスワード変更

教師用の `class` は Scapi の `Session.get_mystuff_classes()` と `get_mystuff_class()` を使い、指定した1ページだけを読む。生徒とクラススタジオもクラスIDを本人のMy Stuffで検証してから、それぞれの一覧APIを1ページだけ呼ぶ。作成・編集・クラススタジオ作成には既存のアカウント確認層を使う。クラスを閉じる場合は通常の `yes` ではなく `close class <id>` の入力が必要で、Scapiの編集成功後に表示用の閉鎖状態を更新する。

スタジオの所有権移譲は `Studio.transfer_ownership(user, password)`、パスワード変更は `Session.change_password(old_password, new_password)` を使う。どちらも対象を含む文字列の入力確認後、パスワードをエコーなしで取得する。パスワードやセッションIDを子プロセスの引数やログへ載せない。パスワード変更後は保存済みセッションが有効とは限らないため、成功時だけローカルログインを消去して再ログインを促す。フォーラム投稿はScapi 3.2.4に投稿メソッドがなく、公開GETメソッドだけでは安全な実装ができないため未対応。

## 公開詳細、通知件数、ニュースID

`project details` と `studio details` は認証なしのScapiクライアントで各対象を1回だけ取得し、CLIが使用するフィールドを明示的にJSONへ変換する。作品ではリミックス親・ルート、説明、クレジット、好き・お気に入り・閲覧・リミックス数を含める。未知値は文字列化せず原則 `None` とする。

通知一覧は未読件数を先に取得し、`--limit` がない場合は `min(未読数, 40)` 件だけを取得する。未読0件なら一覧APIを呼ばない。ScratchニュースのIDはJavaScriptの安全整数を超える場合があるため、Python側で文字列としてJSON化し、TypeScript側も文字列IDを検証する。これにより正しいレスポンスを数値精度の問題で拒否しない。

## ログアウトの検証

Scratchの[公式Webクライアント](https://github.com/scratchfoundation/scratch-www/blob/develop/src/redux/navigation.js)は、`csrfmiddlewaretoken` にCookieと同じCSRFトークンを指定したフォームを `/accounts/logout/` へPOSTする。CLIもURLエンコードしたフォーム本文、Cookie、CSRFヘッダーを揃える。保存されたCSRFがない場合だけ `/csrf_token/` から取得する。

ブラウザは応答の `Set-Cookie` で手元のログインCookieを削除するが、Bunのfetchには同じCookie保存機構がない。自動リダイレクトで途中の `Set-Cookie` を見失い、古いCookieをそのまま再送していたことがログアウトの誤判定につながっていた。`redirect: "manual"` で302/303の応答を保持し、`scratchsessionsid` の空値・有効期限切れを確認してからCLIの認証情報を削除する。Cookie削除がない場合だけ既存Cookieで未ログインを検証し、200というHTTPステータスだけで成功とは判定しない。Scratchの匿名 `/session/` 応答には `user` 自体がなく、既知の `flags` がある形式も受け付ける。

Scapi 3.2.4も `logout()` の要求が無意味な可能性を注記しており、Cookieの削除と、コピー済みトークンのサーバー側失効は別である。CLIは全トークンの失効を保証せず、`--local` を明示した場合は通信なしでCLIの保存済みログインだけを消去する。保存前にセッションが変わっていないことを確かめ、別のログインを消さない。ネットワーク失敗と設定保存失敗は別のエラーとして扱う。

## コマンドを用途から探すヘルプ

`src/commands/help.ts` はトップレベルのコマンド分類と、各コマンドの操作分類・実行例を管理する。基本の名前・引数・選択肢は既存のコマンド定義に残し、分類表示にはその説明を再利用する。`help project` などの既知の対象は `project --help` へ解釈し直してyargsで表示するため、ヘルプのためにプロジェクト操作や認証処理を実行しない。引数なしの `project`、`studio`、`class` も同じ経路を使う。削除済みの `profile` はヘルプや補完にも登録しない。

actionの詳細は `src/commands/action-help.ts` に説明・適用オプション名・必須条件・例を定義する。オプションの型・選択肢・説明は既存のコマンド定義から取得し、実行用のパーサーやハンドラーの仕様は変更しない。全actionのヘルプを生成できることをテストして、新しいactionやオプションを追加した際の定義漏れを検出する。

ヘルプ対象は、ハンドラーを一切登録していないyargsでオプションを解析して判定する。単純に引数配列から `--help` を探すと、`--text=--help` の本文や `--` 以降の文字列までヘルプ扱いしてしまうためである。詳細ヘルプは通常の実行処理へ入る前に表示を終え、ログイン・画像読み込み・変更処理を呼ばない。`help user reply` はヘルプ用のユーザー名を補って、実行構文の `user <username> reply --help` と同じ詳細表示へ解決する。

## スタジオ管理とコメント操作

スタジオ一覧は `Session.get_mystuff_studios()` で指定した1ページだけを取得する。マネージャー・キュレーター・コメント一覧も上限40件で取得し、ページの自動巡回はしない。フォローとコメントは通常のScapi interaction経路を使い、スタジオを退出する、招待する、参加者を外す、作品をスタジオから外す操作は対象アカウントを確認してから実行する。

コメントの報告・削除では `scapi.Comment` に正しい `Project`、`Studio`、`User` の親を渡す。ユーザーのコメントはScapiの旧API切替を有効にして扱う。報告や削除のテストではScapiクラスをモックし、実サービスへリクエストしない。

## オフライン・失効セッションと操作の打ち切り

認証状態を真偽値だけで表すと、「サーバーに到達できず確認できない」を「未ログイン」と誤判定する。`scratch-session.ts` はログイン済み・未ログイン・確認失敗の3状態を返し、既知の応答形式だけを採用する。これにより `login` はオフライン・HTTP 429・不正な応答でパスワード入力や次の通信を始めず、`session` も不正データを正常な未ログインとして表示しない。保存済みセッションは維持する。`user details` では認証時の `ValueError` と `Unauthorized` は再ログインを案内し、認証完了後の不正データや通信エラーと区別する。例外本文やPythonの生の標準エラーは表示しない。

認証用fetchは `AbortSignal.timeout(15_000)` を使用する。Scapi経由の操作は `runtime.py` が操作全体を30秒でキャンセルし、`process.ts` がPythonプロセスの待機を35秒で打ち切る。通信が切れてもサーバーが変更済みの可能性はあるため、タイムアウトを「変更なし」とは表示せず、結果を確かめてから再実行するよう案内する。自動再試行はしない。

`confirmation.ts` は確認入力を共通化し、拒否・EOF・入力エラー・非対話実行を安全な中止として扱う。好き・お気に入り・フォローとその解除、コメント投稿・返信も `confirmAccountAction` を通し、本文を含めた公開内容を表示してから操作する。interaction用Pythonも管理用Pythonと同じ `expected_account` を必須とし、確認時のアカウントと異なる場合は変更しない。テストでは入出力とPythonをモックし、許可・拒否・切替・通信失敗の各経路を検証する。

Python環境の作成とScapiのインストール・更新は、Scratch上の変更とは別の確認を行う。対象の専用環境パスと変更内容を表示し、承認後だけディレクトリ作成・pip実行へ進む。既存環境は再作成しない。確認省略オプションは設けず、環境構築テストでも実際のパッケージ更新は行わない。

## フォーラム閲覧とトピックの購読

`forum` のIDはactionで意味が変わる。`topics` はカテゴリ、`topic`・`posts`・`follow`・`unfollow` はトピック、`post`・`source` は投稿を指定する。引数・件数・ページ番号を通信前に検証し、引数なしの `forum` とactionのヘルプは通信せずに表示する。

まず[Scapiのフォーラム資料](https://scapi.kakeru.f5.si/en/stable/_modules/scapi/sites/forum.html)とインストール済みの3.2.4を確認した。カテゴリ・トピック・投稿の閲覧、`ForumPost.get_source()`、`ForumTopic.follow()` / `unfollow()` は存在するが、新規トピック・返信・編集用メソッドは存在しない。指定されたlatestのサイトAPIページは直接取得できなかったため、最新仕様を網羅確認したとは扱わない。

3.2.4の `ForumTopic.get_posts()` は `blockpost roweven firstpost` だけを対象にしており、他の行形式を取りこぼす。また `ForumPost.update()` は投稿の子要素から `og:url` を探すため、ページのhead内にだけ存在する場合に失敗する。ライブラリのコードをコピー・変更せず、既存のScapi HTTPクライアントで同じ公開ページを取得し、BeautifulSoupで読み取り用フィールドだけを抽出する。全投稿行を `.blockpost[id]` で抽出し、トピックのメタ情報は文書全体から読む。ページ送りがない1ページのトピックにも対応し、未知のHTMLを空の正常結果に置き換えない。

閲覧では保存済みのセッションを使わず、未読状態などのアカウント情報を変更しない。カテゴリ一覧はトップページ、topics/postsは指定ページだけを取得し、本文をプレーンテキスト化する。BBCodeは `get_source()` だけで取得し、投稿の詳細情報を重複取得しない。表示するURLは検証済みIDから組み立て、制御文字を除去する。

トピックのフォロー・解除は `confirmAccountAction` で対象アカウントとトピックを表示する。承認後だけセッションと `expected_account` を標準入力へ渡し、Python側で欠落・不一致を拒否してからScapiの変更メソッドを1回呼ぶ。通信エラー・404・429・認証エラーを分けて扱い、例外本文や認証情報は出力しない。429の `Retry-After` は秒数・HTTP日付を受け付けるが、自動再試行しない。既存の30秒／35秒のタイムアウトを使用し、テストはモックと固定HTMLのみで実行する。

## 状態を指定する設定操作と公開一覧

CLIの `on/off` は「指定した状態にする」という意味であり、呼ぶたびに反転する意味ではない。Scapiの `Studio.toggle_comment()` と `User.toggle_comment()` をそのまま呼ぶと、再実行で意図とは逆の状態になる。そのため `set_boolean_setting` は現在値がbooleanであることを確認し、同じなら変更せず `changed: false` を返す。変更が必要な場合は1回だけ操作して読み直す。不明な現在値なら送信せず、送信後の読取失敗・値の不一致なら未検証のエラーを返す。別のブラウザーからの同時変更まで原子的に排除できるわけではないので、自動再試行・自動的な反転し直しは行わない。スタジオへの公開作品追加権限も同じ確認・検証経路を通す。

Scapi 3.2.4の `Project.edit(comment_allowed=...)` は同じ単数形のキーを送るが、[Scratch公式クライアント](https://github.com/scratchfoundation/scratch-www/blob/develop/src/views/preview/project-view.jsx)は `comments_allowed` を使う。作品の設定ではScapiのHTTPクライアントで正しいキーを送信し、返却された作品IDとbooleanが指定どおりか確認する。HTTP 200だけを成功条件にしない。共有解除はScapiの `unshare()` を使用する。どちらも既存のアカウント確認層を通す。

公開一覧は `resource_collections.py` にまとめ、認証情報を読まない。プロジェクトのコメントと所属スタジオには作者名が必要なため、作品メタ情報を1回取得してから対象の一覧を1回読む。リミックス一覧とスタジオ内作品・活動は一覧取得だけで済み、上限を40以下にしてScapiによる分割取得を防ぐ。廃止されたリミックスツリーは使わない。コメント返信や活動の関連対象を追って自動取得しない。

本人の反応状態には `is_loved()` / `is_favorited()`、スタジオの役職等には `get_my_role()` を使う。これらは読取専用なので確認プロンプトなしで、booleanを検証してから表示する。管理操作の成功応答も確認したアカウント名と照合する。テストはモックで、変更不要・不明値・誤った応答・アカウント切替・失敗後の再送なしを確認する。

## アセットを失わないプロジェクト転送と二段階の確認

古い作品は、現在もScratch 1のバイナリやScratch 2のJSONを返す場合がある。作品600は公開データの読取で `ScratchV02` のバイナリ（648,683バイト）を返すことを確認した。JSONとして読めることや `targets` の存在をすべての作品に要求しない。Scratch 1形式は署名・情報ブロック長・全体容量だけを検査して、Squeakオブジェクトの解釈や実行をせず、そのまま `.sb` で保存する。この検査は作品内部の意味的な正しさを保証するものではない。

Scratch 2のJSONは `objName` と `children` で判定し、スプライトのcostumes/sounds、文字レイヤー、ペンレイヤーを収集する。公式Scratch VMのsb2読込処理を参照すると、ローカルZIPのファイル名にはハッシュでなく `baseLayerID` / `soundID` / `textLayerID` の数値が使われる。サーバーのJSONにはIDが `-1` の場合があるため、保存用コピーに正のIDを割り当て、同じアセットには同じIDを使う。文字レイヤーのIDを0にしないのは、公式ローダーが真偽値として確認しているため。取得するURLとハッシュは従来どおり検証し、数値名のZIPも安全性・容量・欠落・MD5の検証を行う。スクリプトは変換せず `.sb2` として保存する。

Pythonの返却するformatは取得した元形式を示す。保存時は `--format`（既定：sb3）に従って変換し、`original` のときだけ元形式を保持する。`--output` で指定されたScratch拡張子が出力形式と異なる場合は、既存ファイルに書かずにエラーにする。元形式は作成年代ではなく実データで決めるため、Scratch 2時代の作品が既に3形式なら変換不要になる。アップロードは引き続きScratch 3のみで、古い形式を誤って新規作成・上書きへ渡さない。

### 実データを変換してsb3として保存する

拡張子だけの変更では古い作品をsb3として開けないため、`project-conversion.ts` が別Bunプロセスで公式Scratchライブラリを使う。Scratch 1はscratch-sb1-converterで数値名のアセットを持つsb2へ、Scratch 2はScratch VMでブロックを含むsb3へ変換する。sb→sb2、sb→sb3、sb2→sb3に対応し、下位形式への逆変換は明示的に拒否する。変換の失敗・タイムアウト・上限超過では保存せず、`--format original` を案内する。

scratch-sb1-converterのJSONは、空のペンレイヤーに固定のダミーMD5とID 0を指定するが、対応ファイルをZIPには含めない。実際の作品600でsb→sb2のアセット検証を行うと衣装ID 0と衝突したため、空の480×360画像を専用IDで補い、MD5も実際のPNGバイトから設定する。衣装・音声の参照ハッシュも出力バイトから整合させる。作品600では公開データをメモリー上で変換してsb2（8アセット）とsb3（7アセット）の両方を検証した。通常テストにはその作品データを含めず、自作の画像・音声・ブロックを使う。

公式VMのNode配布バンドルはBunでjsdomのCSSを誤った場所から探して失敗したため、固定した15.2.0の同梱ソース入口を使用する。vendorファイルは変更しない。ストレージはローカルZIPのみを使い、レンダラーと音声エンジンを接続せず、greenFlag/startを呼ばない。外部URLの拡張機能を許可せず、公式の組み込みIDだけをロードする。VMが未対応ブロック・モニターを落とす警告を検出したら成功扱いにしない。ターゲット・衣装・音声の数を確認し、出力ZIPを既存のPython検証へ戻して参照アセットとMD5も確認する。

ヘッドレスVMは画像をそのまま保持するので、Scratch 1由来の独立した文字レイヤーを事前に合成する必要がある。追加したMITライセンスの `@napi-rs/canvas` に、URLではなく検証済みのPNG/JPEGバイトだけを渡す。画像は最大16,777,216画素とし、PNGはデコード前にも寸法を検査する。元の画像を共有する別の衣装を壊さないよう、合成画像には新しいローカルIDとMD5を割り当てる。SVGに対する旧エディター特有の描画補正は行わないため、見た目の完全一致が必要なら元形式を使う。Canvasはネイティブ依存を含み、Windows/Linuxでの実機検証はまだ行っていない。

ScratchライブラリはAGPL-3.0-only、CanvasはMIT、JSZipはMITを選択して利用している。元のライセンスを依存パッケージ内に保持し、`THIRD_PARTY_NOTICES.md` に一覧を記載した。プロジェクト自身のライセンスはこの変更では選択していないため、公開配布前に決定・確認が必要である。

### offset方式とAPI固有ページの区別

ページが反映されない疑いを確認するときは、計算関数だけでなくyargs→コマンド→Python起動引数まで通して検証する。検索の回帰テストは実際のCLI入口を使い、Pythonプロセスだけをモックしてpage 1/2/3がoffset 0/10/20になることを確認する。検索結果の表示番号もoffsetを加えた通し番号にし、取得範囲・offset・limitを表示する。番号が毎回1から始まる表示だけでは、内容が変わっていても同じページに見えるためである。実サービスの重複を判断する場合はタイトルだけでなく作品IDを比較し、順位変動やサービス側の応答をCLIの計算ミスと混同しない。

`pagination.ts` は1始まりのpageから `offset + (page - 1) * limit` を計算し、正のページ数・件数上限・安全な整数範囲を検証する。前のページを読むループは使わない。ユーザーの公開作品・フォロー一覧など、これまでoffsetだけだった場所も同じ計算を使う。一方、ユーザーコメントやMy Stuff、フォーラムなどAPI固有のpageがある場所では、その値を従来どおりAPIへ渡す。studio activityはoffsetを持たないため対象外である。

通知は未読数により既定件数が決まるので、pageを標準入力でPythonへ渡し、既に取得している未読数からeffective_limitを計算した後にoffsetを決める。ページ計算だけの追加通信はしない。未読数が変化すると既定ページサイズも変わるため、固定した区切りが必要な利用者には `--limit` を案内する。

ダウンロードの既定ファイル名には、既に取得する作品メタ情報のtitleを使い、名前だけの追加リクエストを発生させない。日本語・絵文字は保持するが、パス区切り・Windows禁止文字・制御文字・双方向制御文字は `_` に置き換える。末尾の空白・ピリオドを除去し、Windowsの予約名には `_` を付け、UTF-8で180バイトまでに制限する（文字の途中では切らない）。空や未取得のtitleはIDに戻す。`--output` があればそのパスを優先する。既定名は取得後に決まるため、同名ファイルの確認も取得後・保存前になる。明示パスでは従来どおり通信前に確認し、どちらも保存時の宛先再検証を行う。

`.sb3` は `project.json` と画像・音声をまとめたZIPであり、JSONだけの取得ではローカル実行に必要な素材が欠ける。[Scapiの移行ガイド](https://scapi.kakeru.f5.si/en/stable/migrating.html)で `Project.download` が削除済みであることを確認したため、`Project.download_url` でJSONを読み、各targetのcostumes/soundsが参照するアセットを重複なく取得してZIPへまとめる。URLは固定のScratchアセットサーバーと検証済みのMD5名から構成し、プロジェクト内に書かれた任意URLへはアクセスしない。

アップロードは[ScapiのサイトAPI](https://scapi.kakeru.f5.si/ja/latest/reference/sites.html)とインストール済み3.2.4の `Session.create_project` / `Project.edit_project` を確認し、既存メソッドにJSONを渡す。画像・音声は先に保存する。[Scratch公式エディターの保存処理](https://github.com/scratchfoundation/scratch-gui/blob/develop/src/lib/project-saver-hoc.jsx)と同様、アセット保存の `status: ok` を確認する。Scapi 3.2.4の `upload_asset` は返却JSONを検証せずハッシュ名だけを返すため、ここはScapiのHTTPクライアントで応答を確認する。失敗したアセットがあればJSONを送らない。JSON保存後も読み戻して内容を比較し、検証失敗を成功として表示しない。

ローカルのsb3検証にはPython標準ライブラリを使う。ZIPをディレクトリへ展開せず、絶対パスや親ディレクトリ参照、シンボリックリンク、暗号化、重複名、未対応の圧縮形式、欠落アセット、不一致のハッシュを拒否する。入力サイズだけでなく展開後の合計・各ファイル・個数も制限し、ZIP爆弾を避ける。上限はアーカイブ50 MiB、展開後100 MiB、アセット200個・各10 MiB、JSON 5 MiB。転送は直列で、後続アセット間に100ms待つ。429やタイムアウト時も自動再試行しない。転送だけPython120秒・親125秒の上限と75 MiBの出力バッファを使い、他の操作の制限時間は変えない。

アップロードするファイルは最初にメモリーへ読み込み、検証後の確認中に元ファイルが変わっても送信内容が変わらないようにする。確認時にアカウント、入力パス、上書き先IDを表示し、既存作品には `overwrite <id>` を要求する。Pythonでも `expected_account` と作品所有者を検証してから書き込む。IDなしは未共有作品の新規作成で、IDありは本体だけを更新し、タイトル・共有状態には触れない。アセットの保存とJSONの保存はサーバー上の単一トランザクションではないので、失敗時にも一部アセットや作品変更が残り得る。自動的な巻き戻しは別の変更を消しかねないため行わず、状態確認を案内する。

ダウンロードのローカル上書き確認は、Scratchへの書込確認とは別に行う。保存先が既存ならファイルの識別情報を保持して確認し、通信後に再確認する。新規保存は同じディレクトリ内の一時ファイルから排他的なハードリンクで確定し、途中で同名ファイルが作られた場合は失敗させる。確認済み既存ファイルは一時保存の完了後にrenameで置き換える。宛先がシンボリックリンクやディレクトリなら拒否する。識別情報の再確認は通常の同時編集を検出するもので、最終確認とrenameの間に別プロセスが競合することまで原子的に排除する仕組みではない。Windows・Linux上での実機検証はまだ行っていない。
